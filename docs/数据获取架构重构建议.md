# 数据获取架构重构建议

## 🎯 重构目标

简化数据获取架构，消除不必要的抽象层，建立清晰的调用链路。

## 📊 当前架构问题

### 当前调用链路

```
页面 → useItemListData → useItemApi → useHttp → $api
     ↑ 不必要的抽象层
```

### 理想调用链路

```
页面 → useItemApi → useHttp → $api
     ↑ 直接调用API层
```

## 🔧 重构方案

### 1. 保留通用工具函数

`useDataFetch.ts` 改为纯工具函数，不包含业务逻辑：

```typescript
// composables/useDataFetch.ts
/**
 * 通用的防重复请求数据获取工具
 */
export function useDataFetch<T>(
  key: string,
  fetcher: () => Promise<T>,
  options: UseDataFetchOptions = {}
) {
  // 只处理通用的数据获取逻辑
  // 不包含任何业务相关的代码
}

/**
 * 通用分页数据管理
 */
export function usePaginatedData<T>() {
  // 纯粹的分页状态管理
  // 不依赖任何API层
}
```

### 2. 页面直接调用 API 层

```typescript
// pages/product-list.vue
<script setup lang="ts">
import { useItemApi } from '~/api/item'

const itemApi = useItemApi()

// 方案1: 直接调用 (适用于简单场景)
const loadProducts = async () => {
  const { data, error, pending } = await itemApi.getList(params)
  // 处理数据...
}

// 方案2: 结合 useAsyncData (适用于 SSR 场景)
const { data, pending, error, refresh } = await useAsyncData(
  'product-list',
  () => itemApi.getList(params),
  {
    watch: [() => route.query],
    server: true
  }
)

// 方案3: 使用通用工具 (适用于复杂场景)
const { data, pending, error } = useDataFetch(
  'product-list',
  () => itemApi.getList(params),
  {
    watch: [() => route.query],
    avoidDuplicateRequests: true
  }
)
</script>
```

### 3. API 层保持职责单一

```typescript
// api/item.ts
export function useItemApi() {
  return {
    // 基础方法
    getList(params: IItemListParams) {
      return useHttp('/goods/items', {
        query: params,
        cache: 'default',
        key: `items-${JSON.stringify(params)}`,
      })
    },

    // 带重试的方法
    getListWithRetry(params: IItemListParams) {
      return useHttp('/goods/items', {
        query: params,
        retry: { maxRetries: 3 },
      })
    },
  }
}
```

## 📋 重构步骤

### 第一步：重构 useDataFetch.ts

- [ ] 移除 `useItemListData` 函数
- [ ] 保留 `useDataFetch` 和 `usePaginatedData` 作为通用工具
- [ ] 移除与 itemApi 的耦合

### 第二步：更新页面调用方式

- [ ] `pages/products-optimized.vue` 直接调用 `itemApi.getList()`
- [ ] 使用 `useAsyncData` 处理 SSR 数据获取
- [ ] 必要时使用 `useDataFetch` 工具函数

### 第三步：统一数据获取模式

- [ ] 制定数据获取规范
- [ ] 更新文档说明
- [ ] 代码 review 确保一致性

## 🎯 重构后的优势

### 架构清晰

- **单一职责**: 每层只负责自己的逻辑
- **低耦合**: 工具层不依赖业务层
- **易维护**: 修改业务逻辑不影响工具函数

### 使用简单

- **直接调用**: 页面直接使用 API 层方法
- **灵活选择**: 根据场景选择合适的数据获取方式
- **类型安全**: 完整的 TypeScript 支持

### 性能优化

- **减少抽象**: 少一层调用，性能更好
- **缓存统一**: 在 useHttp 层统一处理缓存
- **重试统一**: 在 useHttp 层统一处理重试

## 🚀 最佳实践

### 数据获取选择指南

1. **简单数据获取** → 直接调用 API
2. **SSR 数据获取** → useAsyncData + API
3. **复杂数据管理** → useDataFetch + API
4. **分页数据** → usePaginatedData + API

### 示例对比

```typescript
// ❌ 重构前：多层抽象
const { data } = await useItemListData(() => params)

// ✅ 重构后：直接调用
const { data } = await useAsyncData('items', () => itemApi.getList(params))
```

通过这种重构，我们可以得到一个更加清晰、简单、易维护的数据获取架构。
